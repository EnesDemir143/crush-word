## Current Repo Findings

- Mevcut repo Phase 1 seviyesinde: onboarding, home, dictionary loading ve profile persistence var.
- `pubspec.yaml` icinde su an yalnizca `shared_preferences` bulunuyor; yapisal oyun verisi icin SQLite paketi henuz eklenmemis.
- `GameResult` modeli var, fakat onu kalici hale getiren repository/database katmani henuz yok.
- `LocalStorageService` yalnizca string key-value ihtiyaclarini karsiliyor; session checkpoint, result history ve inventory gibi yapisal veriler icin yeterli degil.

## Package Research Findings

### shared_preferences

- Resmi paket dokumani, bu katmanin basit key-value veriler icin uygun oldugunu; kritik verinin yalnizca burada tutulmamasi gerektigini netlestiriyor.
- Bu nedenle kullanici adi ve hafif ayarlar icin uygundur.
- Aktif oyun durumu, skor gecmisi, coin/joker ekonomisi ve resume checkpoint gibi kritik state burada tutulmamalidir.

### sqflite

- Resmi `sqflite` paketi mobile-first SQLite kullanimini dogrudan destekliyor.
- Transaction, batch ve migration mekanizmasi sunuyor.
- Veritabani dosyasini uygulamanin yerel database path'inde tutuyor; bu, skor gecmisi ve active-session restore gibi ihtiyaclara uygun.
- Bu proje mobil odakli oldugu ve veri modeli kucuk/orta olcekte oldugu icin gerektiginden fazla altyapi kurmadan yeterli gucu sagliyor.

### drift

- `drift` daha reaktif ve daha genis kapsamli bir katman sunuyor.
- Ancak bu repo icin mevcut kararlar "agir state-management veya gereksiz altyapi eklememe" yonunde.
- Bu nedenle `drift`, bu faz icin incelenmis ama secilmemis aday olarak kalmali; gereksiz abstraction ekliyor.

## Config Format Findings

### YAML

- Insan icin okunakli olsa da indentation/parse hatalarina daha acik.
- Bu proje icin Flutter runtime'da JSON'a gore belirgin bir avantaj saglamiyor.
- Typed modele parse etmeden once hata yuzeyi daha genis kaliyor.

### JSON

- Flutter tarafinda sade asset + decode + typed model akisina daha uygun.
- Degisebilir sabitleri tek yerde toplamak icin yeterli.
- YAML'a gore daha dusuk operasyonel risk tasiyor.

### Config scope recommendation

- Config-driven olmasi mantikli alanlar:
  - harf puanlari
  - joker fiyatlari
  - zorluk -> grid boyutu / hamle sayisi eslesmeleri
  - frekans agirliklari
  - power threshold'lari
  - baslangic coin miktari
- Code-driven kalmasi gereken alanlar:
  - combo `subsequence` algoritmasi
  - non-overlapping kelime sayisi hesaplama mantigi
  - grid solvability / fallback arama algoritmasi
  - power tile board etkileri
  - persistence/migration akisi

## Recommendation

### Persistence boundary

- `shared_preferences`: `profile.username` ve benzeri hafif ayarlar
- `sqflite`: skor gecmisi, coin bakiyesi, joker envanteri, aktif oturum checkpoint'i

### Config boundary

- `assets/config/game_rules.json`: ayarlanabilir oyun sabitleri
- `lib/src/core/config/`: loader, typed model, validator
- Rule engine: config'ten sabitleri alir ama davranis mantigini kendi kodunda uygular

### SQLite choice

- Primary choice: `sqflite`
- Supporting package: `path`
- Database filename: `word_crush.db`
- Migration strategy: tek `AppDatabase` giris noktasi + integer schema version

### Proposed tables

1. `game_results`
   - Tekil tamamlanmis oyun kaydi
   - Tarih, zorluk, grid boyutu, puan, kelime sayisi, en uzun kelime, sure

2. `player_wallet`
   - Tek satirlik coin bakiyesi
   - Market satin almalari ve oyun ici coin gosterimi icin canonical source

3. `joker_inventory`
   - Joker tipi bazli sahiplik/adet bilgisi
   - Satin alinmis ve kullanilabilir joker envanteri

4. `session_checkpoint`
   - Aktif oturumun board/state snapshot'i
   - `remaining_moves`, `elapsed_seconds`, `current_score`, `board_json`, `power_tiles_json`
   - Coin verisi burada duplicate edilmez; restore akisi `player_wallet` ile beraber okunur

## File-Structure Recommendation

```text
assets/
  config/
    game_rules.json

lib/src/core/
  config/
    game_rules_config.dart
    game_rules_loader.dart
    game_rules_validator.dart
  gameplay/
    models/
    services/
    rules/
  persistence/
    sqlite/
      app_database.dart
      database_provider.dart
      migrations/
      tables/
      mappers/
  repositories/
    profile_repository.dart
    game_history_repository.dart
    wallet_repository.dart
    joker_inventory_repository.dart
    session_checkpoint_repository.dart
```

### Why this structure

- Oyun kurallari UI'dan ayri kalir.
- SQLite adapter detaylari repository'lerden ayri tutulur.
- Phase 2 board/setup ile Phase 3-5 persistence isleri ayni `core` sinirinda bulusur.

## Validation Architecture

- Otomatik testler davranis odakli olmali: hamle dusumu, grid solvability, combo subsequence, power-tile activation, aggregate siralama
- Manuel kontrol listesi ayrica tutulmali: harf puan tablosu sabitleri, joker fiyat sabitleri, UI'da gosterilen metin/fiyat tutarliligi
- Config validator; zorunlu alanlar, threshold sirasi ve beklenen fiyat/puan key'leri icin acilis validasyonu yapmali

## Conclusion

Bu repo icin en dusuk riskli ve en az agirlik getiren secim `shared_preferences + sqflite` ayrimi ile birlikte `config-driven constants + code-driven logic` modelidir. Runtime config dosyasi icin `JSON`, `YAML`'a gore daha uygun ilk secimdir. Eval fazinda bu sinir, tablo listesi, config kapsami ve klasor yapisi dondurulursa sonraki gameplay fazlari daha az geri donusle ilerler.
